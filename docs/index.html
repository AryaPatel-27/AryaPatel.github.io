6. Convert Email Text into Numerical Features¶

I use CountVectorizer to represent each email using word counts. Each column represents a word, and each value shows how many times that word appears in an email.

For example, if the vocabulary contains "free" and "meeting", the email "free free meeting" would be represented as [2, 1].

I learn the vocabulary from the training emails only. I then use that same vocabulary to transform the test emails, preventing information from the test set from influencing feature preparation.

I limit the vocabulary to the 3,000 most frequent training words to keep memory usage manageable when using Gaussian Naive Bayes. This is a practical limit rather than an optimized setting.

How Naive Bayes Uses Probability¶

Naive Bayes uses the features of an email to estimate whether it belongs to the spam or ham class.

It combines three ideas:

  • Prior probability: How common spam and ham are in the training data.
  • Likelihood: How likely the email's features are within each class.
  • Posterior probability: The estimated class probability after considering those features.

The model predicts the class with the higher posterior probability.

The "naive" assumption means that the features are treated as independent when the class is known. Words are not completely independent in real emails, but this assumption simplifies the calculations.

Gaussian Naive Bayes models feature values using normal distributions. Multinomial Naive Bayes models feature counts, which matches the word-count representation used in this notebook.

7. Train the Naive Bayes Classifiers¶

I train two classifiers using the same training emails and word-count features.

  • Gaussian Naive Bayes assumes that feature values within each class follow a normal distribution. Word counts may not fit this assumption well, but I include it for the required comparison.
  • Multinomial Naive Bayes models word-count features and is commonly used for text classification.

Gaussian Naive Bayes requires dense arrays, so I convert its input to that format. Multinomial Naive Bayes can use the sparse matrices directly. Both formats contain the same feature values.

The models learn from the training set only. I then use them to predict whether each test email is ham (0) or spam (1).

8. Compare Model Performance¶

I compare both models on the same test set, treating spam (1) as the positive class.

  • Accuracy: The proportion of all emails classified correctly.
  • Precision: Of the emails predicted as spam, how many were actually spam?
  • Recall: Of the actual spam emails, how many did the model detect?
  • F1-score: A measure that balances spam precision and recall.

I use spam F1-score as the main comparison measure because the classes are unequal and accuracy alone may hide poor spam detection.

6. Compare Outlier Detection Methods¶

I compare four methods using the same valid-price dataset:

  1. Mean ± 3 standard deviations: Flags prices far from the mean. Extreme prices can influence both the mean and standard deviation.

  2. Median and MAD: MAD is the median absolute distance from the median. I flag prices whose absolute modified Z-score exceeds 3.5. This method is less influenced by extreme values.

  3. Percentiles: Keeps prices between the 1st and 99th percentiles. This trims the tails but does not prove that excluded prices are errors.

  4. IQR: Keeps prices between Q1 − 1.5 × IQR and Q3 + 1.5 × IQR, where IQR = Q3 − Q1.

These are alternative rules. I apply each one independently rather than removing rows repeatedly using all four methods.

For this first comparison, I calculate thresholds across all room types. I will also examine thresholds within room types before selecting the final cleaning rule.

Understanding the Median/MAD Rule¶

MAD is the median of the absolute distances between each price and the median price.

I use the modified Z-score:

Modified Z-score = 0.6745 × (price − median) / MAD

The constant 0.6745 is a conventional scaling factor that makes this score comparable to a standard Z-score for normally distributed data. I flag prices whose absolute modified Z-score exceeds 3.5.

My code expresses this same rule as a price interval:

Lower bound = median − (3.5 × MAD / 0.6745) Upper bound = median + (3.5 × MAD / 0.6745)

This method is less affected by extreme prices than the mean and standard deviation. It does not require me to claim that Airbnb prices follow a normal distribution.

prices = airbnb_valid["price"]

# Method 1: Mean ± 3 standard deviations
price_mean = prices.mean()
price_std = prices.std()

mean_lower = price_mean - 3 * price_std
mean_upper = price_mean + 3 * price_std

# Method 2: Median and median absolute deviation (MAD)
price_median = prices.median()
price_mad = (prices - price_median).abs().median()

if price_mad == 0:
    raise ValueError("MAD is zero; modified Z-scores cannot be calculated.")

mad_distance = 3.5 * price_mad / 0.6745
mad_lower = price_median - mad_distance
mad_upper = price_median + mad_distance

# Method 3: 1st–99th percentiles
percentile_lower = prices.quantile(0.01)
percentile_upper = prices.quantile(0.99)

# Method 4: Interquartile range
q1 = prices.quantile(0.25)
q3 = prices.quantile(0.75)
price_iqr = q3 - q1

iqr_lower = q1 - 1.5 * price_iqr
iqr_upper = q3 + 1.5 * price_iqr

thresholds = {
    "Mean ± 3 SD": (mean_lower, mean_upper),

8. Detect Outliers Within Each Room Type¶

The earlier methods used one set of price thresholds for all listings. However, different room types may have different typical prices.

I now calculate the IQR boundaries separately for each room type. This compares a listing with others in the same accommodation category.

I use the standard boundaries:

  • Lower bound = Q1 − 1.5 × IQR
  • Upper bound = Q3 + 1.5 × IQR

These boundaries identify statistically unusual prices. They do not prove that an expensive listing is incorrect. Location and other property characteristics can also affect prices.

In [53]:
room_thresholds = (
    airbnb_valid.groupby("room_type")["price"]
    .agg(
        Q1=lambda values: values.quantile(0.25),
        Q3=lambda values: values.quantile(0.75)
    )
)

room_thresholds["IQR"] = (
    room_thresholds["Q3"] - room_thresholds["Q1"]
)

room_thresholds["Lower Bound"] = (
    room_thresholds["Q1"] - 1.5 * room_thresholds["IQR"]
)

room_thresholds["Upper Bound"] = (
    room_thresholds["Q3"] + 1.5 * room_thresholds["IQR"]

13. Part B Conclusion¶

The original dataset contained 48,895 listings. I excluded 11 listings with zero prices, leaving 48,884 listings for outlier analysis.

The methods produced different results. Mean ± 3 standard deviations removed 388 listings, median/MAD removed 2,916, percentiles removed 867, and the overall IQR method removed 2,972. This shows that the definition of an outlier depends on the rule being used.

The mean-based upper boundary was approximately $873.27, compared with $334 for the overall IQR method. The extreme prices increased the mean and standard deviation, making the mean-based rule more permissive. The percentile method provided explicit cutoffs, but it could also exclude valid low-cost listings.

I selected IQR by room type because entire homes, private rooms, and shared rooms have different price distributions. Their upper boundaries were $392.50, $162.50, and $138 respectively. For example, a $200 listing would be retained for an entire home but flagged for a private room.

The selected method excluded 3,244 listings, or 6.64% of the valid-price dataset, and retained 45,640 listings. The mean price decreased from $152.76 to $121.81, while the median decreased from $106 to $100.

Validation confirmed that all retained prices were positive and within their original room-type IQR boundaries. The final dataset was saved as AB_NYC_2019_price_cleaned.csv.

The excluded listings are statistically unusual under this rule, but they are not necessarily incorrect. Location, property size, and luxury features could explain some high prices.

14. Part B Reflection¶

This part helped me understand why looking only at the average price can be misleading. Before filtering, the mean was $152.76 while the median was $106. The expensive listings pulled the mean upward, so comparing both measures gave me a clearer understanding of typical prices.

I also learned that different outlier methods do not give the same answer. The mean-based method removed far fewer listings than IQR or median/MAD. This helped me understand why I should explain my choice instead of assuming that any statistical method is suitable.

Comparing room types was useful because a price can be reasonable for one category and unusual for another. I chose room-type IQR because it considered this difference. However, it still does not account for every factor, such as location or property size.

My main takeaway is that cleaning data requires judgment. Removing more rows does not automatically create a better dataset. I kept the original data and saved the excluded listings separately so the decisions could be reviewed later.
